# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Uses pnpm as the package manager.

```bash
pnpm dev        # start Vite dev server
pnpm build      # build to dist/
pnpm preview    # preview the production build
pnpm test       # Playwright E2E smoke suite (tests/*.spec.js) — auto-starts its own dev server on :5175
pnpm test:unit  # Vitest unit tests for the pure astronomy math (src/astronomy.test.js)
```

## Architecture

Three.js + Vite app. Source lives in `src/`, `index.html` stays at the project root per Vite convention and loads `/src/main.js`; NASA textures and every other static asset (favicon, manifest, app icons, `og-image.png`) live in `public/` and are copied to `dist/` automatically by Vite — there's no separate asset-copy step in the build script. Screenshots used only by `README.md` live in `docs/`. Within `src/`, the app is split across a few modules by concern rather than one big file:

- **`astronomy.js`** — pure astronomy helpers built on the `astronomy-engine` package, all taking an explicit `date` rather than assuming "now": `computeMoonVisual(date)` (phase/illumination/libration — cheap, observer-independent), `computeMoonState(date, observerCoords)` (adds horizon altitude/azimuth, the parallactic angle, and moonrise/moonset for that calendar day — `SearchRiseSet` searched from local midnight with a 1-day window, so either can legitimately be `null` on a given day since moonrise drifts ~50 min later daily), `getPhaseName`, `azimuthToCompass`, `daysInMonth`, `localNoon` (numeric-field local dates — never UTC-string parsing, to avoid off-by-one-day bugs).
- **`textures.js`** — loads the NASA SVS CGI Moon Kit assets (`lroc_color_2k.jpg` color map, `ldem_3_8bit.jpg` displacement map — see https://svs.gsfc.nasa.gov/4720) once as shared singletons, reused by every view/mesh. `onColorMapReady(callback)` fires once the (visually-dominant, ~450KB) color map has actually arrived — `main.js` uses it to hide the startup loading overlay instead of showing a flash of default-gray moon.
- **`moon-shader.js`** — `sunDirFromPhase(phase)`, the single source of truth for "which way is the sun" (both the grid and the detail view derive their lighting from it), and `createMoonCellMaterial`, a small self-lit `ShaderMaterial` (no scene lights) used for grid-cell thumbnails.
- **`moon-detail.js`** — the single "moon as seen from here" 3D view (`createMoonDetailView`): `MeshPhongMaterial` moon with displacement/bump, `DirectionalLight` + dim `HemisphereLight`, procedural star field, `OrbitControls` (pan disabled, `minDistance`/`maxDistance` clamped so you can't clip through the surface or zoom the moon down to nothing). `live: true` (the "Today" nav entry) recomputes from the real clock every 30s; `live: false` is a static snapshot at local noon on a given date, reached by clicking a calendar cell, with a "back to calendar" button. `camera.fov` isn't a fixed constant — three.js's `fov` is always *vertical*, so on a narrow/portrait screen the implied horizontal FOV shrinks enough to crop the moon at the sides even at the default (non-zoomed) camera distance; `computeFov(aspect)`, called from `resize()`, widens the vertical FOV just enough to keep the moon's true angular size (`asin(radius / distance)`, not `atan`) inside frame with margin, and is a no-op for `aspect >= 1` (landscape/desktop).
- **`moon-grid.js`** — the calendar-grid view (`createMoonGridView`): one low-poly sphere per day (shared geometry, per-cell `ShaderMaterial` from `moon-shader.js`), laid out by day-of-month × month (matching the reference lunar-calendar poster, not a Sun–Sat week grid), with month-name/day-number labels as canvas-texture sprites in the same 3D scene. Month view and year view are the same builder — year view just passes all 12 months. Cell/label positions aren't fixed at construction — `applyLayout()` recomputes them every `resize()`, because the grid **transposes** based on viewport orientation (`height > width`): landscape/desktop keeps days as columns and months as rows (the horizontal poster); portrait/mobile swaps them so days run vertically (a scrollable list) and months become columns, since vertical scrolling is the natural mobile gesture. `resize()` also keeps cells at or above `MIN_CELL_PX` (a legible/tappable diameter); when the full grid can't fit the viewport at that size, the view zooms to the minimum and becomes pannable instead of shrinking further — drag/swipe pans (clamped to content bounds, whichever axis needs it), a tap under `DRAG_THRESHOLD_PX` of movement raycasts to find the date and hands off to the detail view. New/full moon days get a ring-sprite halo (`getRingMaterial`, a shared texture) — found per cell by comparing its phase's distance to new/full against its immediate neighbors (a local-minimum check, not a fixed threshold). Keyboard: the canvas gets `tabIndex`/`role="application"` only while a grid is mounted; arrow keys move a `focusedCell` along whichever axis is currently on-screen (translated through `transposed`, so Left/Right/Up/Down always match what's visually there), Enter/Space selects, and movement auto-pans via `ensureVisible()` if the focused cell would fall outside the current pan window. `focusedCell` (keyboard) and `hoveredCell` (mouse) drive one shared `activeCell` visual — the label crosshair plus a `CELL_ACTIVE_SCALE` bump on the cell mesh itself. The grid canvas is full-bleed behind the fixed-position nav/icon cluster, so without correction the top-left content (day 1) would render right under them — `getTopInset()` (passed in from `main.js`, a live measurement of both elements' actual `getBoundingClientRect()`) is converted to world units each `resize()` and folded into `panBounds()`'s `maxY`, so panning (initial, drag, or keyboard `ensureVisible`) can never scroll content underneath that overlay, at any zoom level or screen size.
- **`location.js`** — `createLocationState()` returns a shared, mutable `location` ref (`{ coords, status }`, `status` one of `idle | pending | granted | denied | unsupported`) plus `requestLocation(onChange)`, only ever called when the user clicks "Use my location." Views read `location.coords/status` fresh on every refresh rather than being pushed an update, so a later grant still reaches whichever view is active at the time — `onChange` is just how the caller (`main.js`) knows to trigger that refresh.
- **`url-state.js`** — `syncUrl(state)` (`view`/`year`/`month`/`date` query params via `history.replaceState` — no new history entries per navigation) and `setViewFromUrl(state, setView)`, called once on page load to restore it, falling back to `today` for anything missing or malformed. Both use `window.location` explicitly, never bare `location` — this module has no local binding named `location` to shadow it (unlike `main.js`, which does).
- **`chrome-buttons.js`** — `createChromeButtons({ nav, announce, onToggleRings })` builds the top-right icon cluster (`#chrome-buttons`: About modal, a rings toggle, a share/copy-link button) and returns `{ ringsButton, layoutChromeButtons, getTopInset, getShowRings }`. `#app-nav` (top-center, owned by `main.js`) and `#chrome-buttons` (top-right) are two independently fixed-position elements rather than one shared container — `layoutChromeButtons()` measures both elements' actual `getBoundingClientRect()`s (called after every `setView()`, since nav width/height and the icon cluster's own width both change per view, and on window resize, which this module wires up itself) and only drops the icon cluster below the nav, via an inline `top`, when they'd truly overlap; otherwise it stays at its default top-right CSS position. This replaced an earlier hand-picked-breakpoint approach that kept drifting out of sync with actual content width. Also owns the rings-visibility flag itself (persisted to `localStorage`, `getShowRings()` exposes it to callers) since it's UI state that belongs with the toggle that controls it, not with app navigation.
- **`main.js`** — thin app shell: owns the one shared `WebGLRenderer`/canvas and `requestAnimationFrame` loop, renders the top nav (Today / Month / Year + prev/next — the stepper is present on every view, including "Today": stepping away from it leaves live mode and becomes a normal `detail` view for that date, with "Today" as the way back), and `setView()`, which disposes the current view and mounts the next — exactly one view is ever live at a time. Wires together `location.js`, `url-state.js`, and `chrome-buttons.js` rather than owning any of geolocation/URL-sync/chrome-button logic itself. Owns a visually-hidden `aria-live` region (`.sr-only`, `announce(text)`) passed into every view constructor, since the grid's WebGL canvas has no DOM content for a screen reader to read on its own. **Naming gotcha**: the local `const { location } = createLocationState()` (geolocation state) shadows the global — code in this file that needs the URL must say `window.location` explicitly, never bare `location` (this is exactly why `url-state.js` is a separate module: it needs no `location` binding at all).

Mobile/touch: `#bg` has `touch-action: none` and the viewport meta tag disables pinch-zoom, so the page's own gestures (OrbitControls drag/pinch in the detail view, drag-to-pan in the grid) don't fight the browser's native touch handling. The top nav wraps to two rows under `@media (max-width: 480px)` when Today/Month/Year won't fit one line with the month/year/day stepper (which further changes its width/height, another reason `layoutChromeButtons()` re-measures rather than assuming a fixed nav size).

Important gotcha carried through all of this: three.js textures default to `THREE.NoColorSpace`, not sRGB — color maps render far too dark/flat without `texture.colorSpace = THREE.SRGBColorSpace` (the renderer's own `outputColorSpace` already defaults to `THREE.SRGBColorSpace`, but `main.js` sets it explicitly for clarity). `moon-shader.js`'s custom `ShaderMaterial` bypasses the renderer's output-encoding pipeline entirely and does its own raw sampling — verify new shader work still looks right rather than assuming the encoding is handled.

`textures.js`'s `TextureLoader` URLs are root-absolute (`/lroc_color_2k.jpg`, `/ldem_3_8bit.jpg`) rather than module-relative, since they're plain runtime string paths resolved against the page origin, not `import.meta.url` — this also means moving `textures.js` around within `src/` never affects where they resolve.

## Testing

- `tests/*.spec.js` — a small Playwright E2E smoke suite (not exhaustive coverage), kept at the project root rather than under `src/` since it drives the built app rather than importing app modules. `playwright.config.js` auto-starts its own Vite server on port 5175 via the `webServer` option, so `pnpm test` doesn't collide with a manually-running `pnpm dev`. Where a test needs to "select a grid cell," it drives the grid's own keyboard support (focus the canvas, press Enter) rather than clicking canvas pixel coordinates — the grid has no per-cell DOM, so pixel coordinates depend on current layout/zoom and are fragile (this bit us repeatedly during manual testing before the keyboard path existed).
- `src/astronomy.test.js` — Vitest unit tests for the pure functions in `astronomy.js` (phase-name buckets, compass directions, leap-year-aware `daysInMonth`, `localNoon`'s month-boundary rollover, `computeParallacticAngle`'s "directly overhead → zero tilt" invariant). `vitest.config.js` scopes Vitest to `src/*.test.js` only and excludes `tests/` so it never tries to run the Playwright specs. **Pinned to `vitest@^0.34`** deliberately — this project's `vite@^3.0.7` is well behind what current Vitest majors require as a peer (5.x wants vite ^6/7/8); don't blindly upgrade vitest without also reconsidering vite.
